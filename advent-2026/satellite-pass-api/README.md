# Day 07（12/7 月）衛星の通過予測API

- **アプリ名（フォルダ名）**：`satellite-pass-api`
- **ジャンル**：宇宙
- **完成形**：API
- **組み合わせるデータ**：CelesTrak × Open-Meteo（雲量）
- **AI・技術の見どころ**：軌道計算＋自然文の応答

## 作るもの

場所を入れると、ISSなどが見える時刻・方角・高さと、その時間に晴れているかを返すAPI。「今週いちばん見やすいのは？」にも自然文で答える

## 使い道

観測や撮影の計画。前日の「人工衛星は今どこ？」の計算をAPIとして切り出す

## 使い方

デモ：（公開後に記入）

### 画面

1画面に収まる作り（広い画面ではスクロールしない）。左が操作、右が空のドーム。

1. 「通過を調べる」タブで、場所（「札幌市」「Tokyo」など）を入れるか「現在地」を押し、衛星と日数を選んで「調べる」
2. 見える通過が時刻順に並ぶ。「順位」の下の「89点」は見やすさの点数（100点満点。高さ・見える時間・雲量から計算）で、順位はこの点数の順。見え始め・いちばん高いとき・見え終わりの時刻と方角、見える時間、その時刻の雲量が出る
3. 右の空のドーム（three.js）に、選んだ通過の通り道を描き、衛星を30倍速で動かす。光る線が見える部分、点線は地球の影の中や10度未満で見えない部分。ドラッグで回せる。「見上げる」で観測地の真ん中から空を見上げる視点になる（`?view=inside` でも開ける）
4. 「AI に聞く」タブに「札幌で今週いちばん見やすいのは？」のように書くと、AI が答える。地名のない質問は、「通過を調べる」で調べた場所について答える。答えの通過は表とドームにも出る
5. 「API の使い方」タブに、3つの API のパラメーターと、今の入力に合わせた `curl` のコマンド（コピーできる）、その画面で実際に受け取った応答（実行結果）が出る（`?tab=api` で直接開ける）。AI への質問は回数に限りがあるので、このタブからは実行しない
6. 右上の「English」で英語、「この画面について」で「見える」の条件・点数の付け方・精度・出典の全文が出る（画面の下にも出典を常に出す）

### API

| | 内容 |
| --- | --- |
| `GET /api/passes` | 見える通過。`lat`・`lon`（または `place`）、`sat`（NORAD 番号か名前。既定は ISS）、`days`（1〜7）、`lang`、`path=1`（各通過に空の通り道 `path` を付ける。見え始めの2分前〜見え終わりの2分後を5秒ごと、`[見え始めからの秒, 方位角, 高さ, 見えるなら1]`） |
| `POST /api/ask` | 質問に自然文で答える。`{"question": "...", "lang": "ja", "lat": ..., "lon": ...}`（`lat`・`lon` は質問に地名がないとき用）。全体で1日10回・IP ごとに3回 |
| `GET /api/sats` | 予測できる衛星の一覧（CelesTrak の stations と visual。約170機） |

```sh
curl "https://（デモの URL）/api/passes?place=札幌市&days=3"
curl -X POST https://（デモの URL）/api/ask -H "Content-Type: application/json" -d '{"question": "札幌で今週いちばん見やすいのは？"}'
```

時刻は UTC（`time`）と観測地の時刻（`localTime`、時差つき）の両方を返す。キーは不要で、ほかのサイトからも呼べる（CORS を許可）。

### 手元で動かす

```sh
cd advent-2026/satellite-pass-api
pnpm dev     # http://localhost:5207（最初の1回だけ CelesTrak から stations と visual を取って data/ に保存する）
pnpm eval    # NASA の予測との比較（NASA の XML と都市の座標は data/ に保存して使い回す）
```

## 実装メモ

### 計画（2026-11-24、実装前）

**調べてわかったこと**

- **NASA Spot the Station**：旧サイトの都市ごとの RSS（`spotthestation.nasa.gov/sightings/...`）は 404。いまは Day06 と同じ NASA の S3 に、都市ごとの見える時刻の XML がある（`iss-coords/current/ISS_sightings/XMLsightingData_citiesINT01〜.xml`、`citiesUSA01〜`。毎日更新、パブリックドメイン）。日本は INT03 に東京・札幌など数十都市、1都市あたり約10回分。項目は「現れる時刻（UTC、分単位）・見える時間・最大の高さ・現れる方角（例：10 above NW）・消える方角」。**都市の緯度経度は入っていない**ので、評価では都市の座標を別に用意する
- **Open-Meteo**：雲量の予報（`hourly=cloud_cover`、1時間ごと、7日分）と、地名の検索（Geocoding API）がキーなしで使える。地名は「札幌市」「Sapporo」では見つかるが「東京」では見つからない（「東京都」「Tokyo」なら見つかる）。無料版は**非商用**・CC BY 4.0（Day04 と同じ条件。広告は付けない）
- **CelesTrak**：Day06 と同じく、取得は数時間おき。ISS・天宮などは小さな分類（`stations`）、明るい衛星は `visual`（約150機）にある

**作るもの**

| 部分 | 内容 |

### 結果（[eval/RESULTS.md](eval/RESULTS.md)）

- **NASA と同じ通過が見つかった割合**：17都市（日本10・世界7）で 188 / 189（99%）
- **見え始めの時刻**：95% が同じ分、99% が ±1分以内。軌道要素の元期から14日後まで、ずれは中央値 10〜21 秒で、ほとんど広がらない
- **最大の高さ**：差の中央値 0 度、96% が ±2度以内
- **方角**：現れる方角は 99%、消える方角は 93% が16方位で一致（隣の方位まで含めるとどちらも 100%）
- **こちらにだけある通過**：9。うち8は、通過の途中で空が暗くなる・明るくなる（太陽の高さがちょうど −6 度）もので、NASA は載せていないことが多い。残り1つは那覇の1秒だけの通過
- **計算の速さ**：ISS の14日分の通過を探すのに約70ms
- **AI**：試した3つの質問（札幌・ロンドン〈英語〉・大阪の天宮）で、答えの中の数字はすべて計算結果と一致した

### ハマったところ

- **公開した直後に CelesTrak が止まっていた**（2026-11-26）：CelesTrak が HTTP 503 を返していて、新しいプロジェクトには保存した軌道要素がまだないので、画面も API も「軌道のデータを準備できていません」になった。さらに、取得に失敗しても「取得中」の目印が10分残る作りだったので、CelesTrak が戻っても10分は取りに行かなかった。失敗したら1分後に取り直すようにし、保存したものがないあいだは、ほかの人の取得を最大8秒待つようにした。1度取れれば Redis に3日間残るので、それ以降に CelesTrak が止まっても古い軌道要素で答えられる（応答の `elementsStale` が true になる）
- **Spot the Station の RSS がなくなっていた**：昔の都市ごとの RSS（`spotthestation.nasa.gov/sightings/...`）は 404。data.nasa.gov のカタログをたどると、Day06 で使った ISS の軌道データと同じ NASA の S3 に、都市ごとの XML があった。ただし都市の緯度経度は入っていない
- **雲量98%の通過が1位**：はじめは見やすさの点数を「高さ60点＋雲量30点＋時間10点」の足し算にしていたら、ロンドンで真上を通るが雲量98%の通過が1位になった（AI は「雲で見えないかもしれない」と書いてはいた）。雲量を掛け算にして直した
- **「東京」が見つからない**：Open-Meteo の地名検索は「東京」では見つからず、「東京都」「Tokyo」なら見つかる。見つからなければ「市・都・府・県」を足して試すようにした。AI の質問の読み取りでは、正式な地名に直してから渡す
- **真上に近い通過の「いちばん高いときの方角」が揺れる**：札幌の高さ85度の通過で、同じ通過なのに計算するたびに SSW（南南西）になったり SW（南西）になったりした。真上の近くでは、1秒で方位角が大きく変わるため（いちばん高い時刻が1秒未満ずれるだけで変わる）。高さが80度を超える通過では、いちばん高いときの方角にはあまり意味がない。なお、AI の答えの方角は、AI に渡した値と一致していた（方角の言葉は自動では照合していない）

### 限界

- 予測の精度は軌道要素の新しさに頼る。ISS は数週間ごとに軌道を上げる（リブースト）ので、その直後は時刻が数分ずれうる。2時間ごとに新しい軌道要素を取るので、公開デモでは毎回新しいものを使う
- 影は円柱で近似していて、半影（少し暗くなる部分）は考えていない。消える方角が隣の方位になるのは、主にこのため
- 明るさ（等級）は計算していない（決めたこと）。暗い衛星は条件を満たしても肉眼では見えないことがある
- 高さが80度を超える通過では、いちばん高いときの方角は計算のたびに隣の方位に変わることがある（真上の近くでは方位角が急に変わるため）
- 雲量は1時間ごとの予報で、7日先までの全体の雲量だけ。低い雲・高い雲の違いや、山や建物の影は考えていない
- NASA と比べられたのは ISS だけ。天宮などは同じ計算だが、答え合わせはしていない

### AI の振る舞いで面白かった例

- 札幌：「いちばん見やすいのは 11/29 17:22、高さ85度（ほぼ真上）…雲を重視するなら 12/1 の通過（雲量8%）も候補」と、順位はそのままに別の選び方も添えた
- ロンドン（英語）：点数の付け方を直す前、雲量98%の通過が1位だった。AI は順位を変えずに「the view may be blocked」と書き、2位を backup として勧めた。ルールを守ったうえで利用者を助けた例で、点数の付け方の欠陥に気づくきっかけにもなった
