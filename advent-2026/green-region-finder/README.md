# Day 03（12/3 木）CO2の少ないクラウドリージョン

- **アプリ名（フォルダ名）**：`green-region-finder`
- **ジャンル**：インフラ
- **完成形**：Webアプリ
- **組み合わせるデータ**：Ember × リージョン所在地 × Google Cloudの公開カーボンデータ
- **AI・技術の見どころ**：推薦

## 作るもの

利用者の場所と要件を入れると、通信の近さを条件にして、電力のCO2が少ないリージョンを提案する（料金は扱わない。2026-11-23 決定）

## 使い道

インフラ設計や、バッチ処理をどこで動かすかの判断

## どんな効果があるか

### 一言でいうと

**同じ処理でも、サーバーを置く場所を変えるだけで、電力の CO2 を半分〜9割以上減らせる場合がある。** その「どこに置けばよいか」を、遅延の条件を守った範囲で見つける。

電力1kWhあたりの CO2 は、国や地域の発電方法（石炭・ガスか、水力・原子力・再エネか）で10倍以上違う。たとえば日本は約474 g、ノルウェーは約28 g（Ember、2025年）。クラウドなら、プログラムを変えずにリージョンを変えるだけで、この差をそのまま利用できる。

### どれくらい減るか（試算）

同じ量の電力を使う処理を、最寄りのリージョンから提案されたリージョンに移した場合の CO2。2026-11-23 時点のデータでこのアプリが計算した値。

| 場所・要件 | 最寄り → 提案 | 電力1MWhあたりの CO2 | 削減率 | 遅延の目安 |
| --- | --- | --- | --- | --- |
| 東京・リアルタイム | 東京 → 釜山 | 474 kg → 418 kg | −12% | 5 → 18 ms |
| 東京・Web アプリ | 東京 → ニュージーランド | 474 kg → 96 kg | **−80%** | 5 → 128 ms |
| 東京・バッチ処理 | 東京 → ノルウェー | 474 kg → 28 kg | **−94%** | 5 → 248 ms |
| シンガポール・Web アプリ | シンガポール → ニュージーランド | 497 kg → 96 kg | −81% | 5 → 119 ms |
| ロンドン・リアルタイム | ロンドン → ノルウェー | 218 kg → 28 kg | **−87%** | 5 → 20 ms |
| ニューヨーク・リアルタイム | バージニア → モントリオール | 357 kg → 192 kg | −46% | 10 → 12 ms |

イメージしやすいように、**平均100Wで1年中動くサーバー1台（年876kWh）**と仮定すると：

- 東京のまま：年 **約415 kg**
- バッチ処理をノルウェーへ：年 **約25 kg**（約390 kg 減る）
- Web アプリをニュージーランドへ：年 **約84 kg**（約331 kg 減る）

100Wは説明のための仮の値。実際の消費電力はサーバーの種類や使い方で大きく変わる。データセンターの冷却などの電力（PUE）も含めていない。

### 効果が大きいのはどんなとき

- **遅延を気にしない処理**（夜間のバッチ処理、機械学習の学習、動画の変換、バックアップ）：世界中から選べるので、北欧・フランス・カナダなど CO2 が非常に少ないリージョンを使える。削減率が最も大きい
- **ヨーロッパや北米東部の利用者向けのサービス**：近くに CO2 の少ないリージョン（北欧、モントリオール）があるので、リアルタイムの用途でも遅延をほとんど増やさずに減らせる（ロンドン → ノルウェーで −87%、+15ms）
- **日本の利用者向けのリアルタイムのサービス**：近くに CO2 の少ないリージョンがないので、効果は小さい（−12%）。このアプリは「効果が小さい」こともそのまま示す

### 誰の役に立つか

- **新しくサービスを作る開発者・インフラ設計者**：リージョンを決める前に、遅延と CO2 の両方を比べられる
- **機械学習やバッチ処理を回すチーム**：重い処理だけを CO2 の少ないリージョンに移す判断材料になる
- **サステナビリティの担当者**：「リージョンを変えたら CO2 がどれくらい変わるか」の見積もりの出発点になる（ただし、正式な排出量の報告には各社が出す数字を使うこと）

### 注意

- ここでの CO2 は「その地域の電力網の平均」（location-based）。各社が買っている再エネ電力（PPA など）は含まないので、各社が公表する排出量（market-based）とは別の数字
- 遅く（遠く）なる分、データの転送量や利用者の体感、データを置ける国の決まりなど、ほかに考えることが増える。このアプリは遅延と置ける国だけを条件にしている
- 料金は扱っていない（ただし、Azure の料金と CO2 にはほぼ関係がなかった。CO2 を減らしても高くなるとは限らない）

## 確かめ方（評価）

Emberの国別データから出した推定値を、Google Cloudが公開しているリージョンごとのカーボンデータと比べる

評価のスクリプトと結果は `eval/` に置く。

## 使い方

### こんなときに使う

| 場面 | 選ぶもの | 見るところ |
| --- | --- | --- |
| 新しいサービスのリージョンを決める | 利用者が多い場所・「Web アプリ」 | 1位と「最寄り」の CO2 と遅延の差。差が小さければ最寄りでよい |

### 画面の使い方

1. **利用者の場所**を選ぶ（東京・ロンドンなどのボタン、地図をクリック、または「現在地を使う」）
2. **要件**を選ぶ
   - リアルタイム（ゲーム・通話など）：遅延 50ms 以内
   - Web アプリ・API：遅延 150ms 以内
   - バッチ処理・学習：遅延の条件なし
3. 必要なら**クラウド**（Google Cloud・AWS・Azure）と**データを置ける国**を絞る
4. 上の欄に「最寄りのリージョンの代わりにこれを使うと CO2 を何%減らせるか」が出る。地図の色が濃い緑ほど CO2 が少ない
5. 「説明してもらう」を押すと、AI（Claude）が理由と注意点を説明する

## 実装メモ

### 試してわかったこと（2026-11-23）

- **Ember**：API はキーが必要だが、**一括 CSV はキーなしで取れる**（国別：`release_generation_yearly_global.csv` 16MB、米国の州別：`release_us_subnational_generation_yearly.csv` 2MB）。「Electricity source = Total generation」の行の「Emissions intensity (gCO2e/kWh)」が、その国・州の電力1kWhあたりのCO2。2025年分まである。古い URL は「もう更新しない」という案内と新しい URL を返す
- **Google Cloud のカーボンデータ**：GitHub の `GoogleCloudPlatform/region-carbon-info`（Apache 2.0）。2019〜2025年の年ごとの CSV。2024年は44リージョン。列は「Google CFE（カーボンフリー電力の割合）」と「Grid carbon intensity（gCO2eq/kWh）」
- **国単位では Ember と Google の値が近く、米国の州単位では大きくずれる**（2024年）

  | 場所 | Ember | Google |
  | --- | --- | --- |
  | 日本（東京） | 484 | 453 |
  | インド（ムンバイ） | 703 | 679 |
  | フィンランド | 67 | 39 |
  | アイオワ州 | 275 | 413 |
  | オレゴン州 | 222 | 79 |
  | サウスカロライナ州 | 290 | 576 |

  州の境と送電網の区域が一致しないため（オレゴンは水力の多い北西部の送電網、サウスカロライナは南東部の送電網に属する）と考えられる
- **料金と CO2 はほぼ無関係**：Azure の D2s v5（35リージョン）の料金と Ember の CO2 の相関係数は 0.02。スウェーデン（$0.102、35g）のように「安くて CO2 も少ない」リージョンがある。このアプリでは料金を扱わないことにした（CO2 に配慮した選択に絞る）

### 実装してわかったこと（2026-11-23）

- **距離だけで遅延を推定すると、海をまたぐ区間で大きく外れる**：東京〜スウェーデンは大円距離 8,100km で、距離だけだと約110ms。Azure の実測は253ms（回線はシベリアの上を通らず、米国経由やインド洋経由で遠回りする）。最初の版は、東京から「Web アプリ（150ms 以内）」で北欧を1位に出していた
  - Azure が公開しているリージョン間の往復時間の実測値（54リージョン、P50、Microsoft Learn の記事の元の Markdown に CSV が入っている）を使い、「利用者 → 最寄りの Azure リージョン →（実測）→ 目的地に最寄りの Azure リージョン → 目的地」で推定するようにした
  - 近い場所（2,000km未満）は中継点を通すとかえって外れる（ニューヨーク〜バージニアが、トロントより遅く出た）ので、距離だけで推定する
- **国の平均では、国の中の送電網の違いが見えない**：大阪の Google の公式値は296 g で、日本の平均（484 g）よりかなり少ない（関西の送電網は原子力の比率が高いためと考えられる）。米国は州単位にしても、州の境と送電網の区域が一致しない（サウスカロライナ州の推定290 g に対し、公式値は576 g）
- **Ember の古いダウンロード URL は「もう更新しない」という案内だけを返す**：案内にある新しい URL に切り替えた
- **共通部品**：Day01 の「回数の上限とキャッシュ」を `packages/store` に切り出し、Day01 もそれを使うようにした（キーの作り方は同じなので、保存済みのキャッシュはそのまま使える）

### 作るもの（完成形）

- **Web アプリ**（Vercel）。地図の上に3社のリージョンを CO2 の色で表示する
- 入力：利用者の場所（地図をクリック、または現在地）、要件（リアルタイム 50ms 以内 / Web 150ms 以内 / バッチ どこでも）、対象のクラウド、データを置ける範囲（国内のみ / どこでも）
- 出力：条件を満たすリージョンを CO2 が少ない順に。「いちばん近いリージョンの代わりにこれを使うと CO2 が何%減り、遅延が何ms増えるか」。AI による理由の説明

### 処理の流れ

```
（事前）リージョンの所在地一覧（3社・都市と緯度経度・国・米国は州）を data ファイルとして作る
（事前）Ember の CSV から国別・州別の最新年の CO2 を取り出して小さな JSON にする
（事前）Google の公式値（最新年）も JSON にする
  ▼
利用者の場所・要件
  │ ① コード：各リージョンまでの距離 → 遅延の推定（RTT ≈ 距離 × 回り道の係数 ÷ 光ファイバーの速さ × 2 ＋ 固定分）
  │ ② コード：条件で絞り、CO2 の少ない順に並べる。いちばん近いリージョンと比べた削減率と遅延の差
  ▼
  │ ③ Claude：上位の提案について、理由と注意点（データの年、州と送電網のずれ、再エネ契約は含まない、など）を説明
  ▼
  ④ コード：説明の数字の照合
```

- CO2 は「その地域の電力網の平均（location-based）」。各社が買っている再エネ電力（PPA など）は含まない。Google の「CFE%」は参考として表示する
- 遅延の推定は距離だけによるもので、実際の回線の経路は反映しない

### 評価の結果（2026-11-23）

詳細は [eval/RESULTS.md](eval/RESULTS.md)。

**A. CO2：Ember からの推定値 と Google Cloud の公式値（2024年、44リージョン）**

| 推定のしかた | 誤差の中央値 | 誤差率の中央値 | 順位の相関 | CO2 の少ない上位10の一致 |
| --- | --- | --- | --- | --- |
| 国単位 | 64 g | 31% | 0.88 | 9 / 10 |
| このアプリ（米国は州単位） | 64 g | 33% | 0.89 | 9 / 10 |

- **値は3割ほどずれるが、「CO2 の少ない順」の並びはよく合う**。リージョンを選ぶ目的なら、Ember の国・州の平均で十分に使える
- 米国を州単位にしても、ほとんど良くならなかった（送電網の区域と州の境が違うため）
- ずれが大きかったのは、ダンマーム（サウジアラビア、公式382 g・推定688 g）、サウスカロライナ州（576 g・290 g）、大阪（296 g・484 g）など

**B. 遅延：推定値 と Azure の実測値（902組。推定にはその2つのリージョン自身の実測値は使わない）**

| 推定のしかた | 誤差の中央値 | 誤差20ms以内 | 「150ms以内か」の判定が一致 |
| --- | --- | --- | --- |
| 距離だけ | 18 ms | 55% | 78% |
| **このアプリ（中継点つき）** | **13 ms** | **65%** | **89%** |

- 距離だけの推定が大きく外れたのは、ブラジル〜南アフリカ（実測321ms・距離だけ102ms）、韓国〜スウェーデン（260ms・101ms）など。中継点つきでは333ms・242ms

### 評価（確かめ方）

- Google Cloud の44リージョンで、**Ember から出した推定値と Google の公式値を比べる**
  - 誤差（平均絶対誤差、平均の誤差率）、順位の相関
  - 国単位だけの推定と、米国は州単位にした推定の比較
  - 「CO2 の少ない順」の上位が、推定値と公式値でどれくらい一致するか（提案が変わってしまうか）

### 一言でいうと

「サーバーをどこに置けば電力の CO2 を減らせるか」を、遅延の条件を守りながら提案する Web アプリ。CO2 を公開していない AWS と Azure も含めて、公開統計（Ember）から推定する。推定の正しさは Google Cloud の公式値で確かめ、遅延は Azure の実測値で補正した。料金は扱わない。

### AI の振る舞いで面白かった例

- 「ニュージーランドの電力は水力・地熱・風力の比率が高い」と、電源の特徴を数字なしで説明した（数字は書かないように指示した）
- 東京リージョンの推定値（474 g）と Google の公式値（449 g）の両方に触れ、推定であることを注意点として書いた
- 説明の数字はすべて渡した値と一致した（照合で不一致0）

### ハマったところ（記事向けの言い方）

1. 距離から遅延を推定したら、東京から北欧が「110ms」になり、Web アプリ向けの1位に北欧が出た。実測は253ms
2. 中継点を使うようにしたら、今度はニューヨークから近いバージニアが、もっと遠いトロントより遅く出た → 近距離は距離だけに戻した
3. Ember の CSV の URL が変わっていて、古い URL は「もう更新しない」という1行の案内だけを返した
4. 国の平均では、大阪（関西）と東京の違いが見えない。米国の州単位も、送電網の区域とずれる

### 正直に書いておくこと（限界）

- CO2 は国・州の年平均。時間帯（昼の太陽光、夜の火力）や、国の中の送電網の違いは反映しない
- 各社が買っている再エネ電力（PPA など）は含まない。各社が公表している「再エネ100%」とは別の数字
- AWS と Azure の推定の正しさは確かめられない（公式値がない）。Google Cloud のリージョンで確かめた結果から類推している
- 遅延は Azure の自社回線の中の実測値をもとにした推定。利用者の家や会社からのインターネットの区間は含まない
- 料金、使えるサービス、データの置き場所の法規制は扱わない
- リージョンの座標は都市単位（データセンターの正確な場所ではない）

### スクリーンショットの候補

- 東京・Web アプリで「CO2 を 80% 減らせます」と出ている見出しと、地図の緑の点線
- 要件を「バッチ処理」に変えたとき、提案が北欧に変わるところ
- ニューヨーク・リアルタイム（ほぼ同じ遅延で −46%）
- AI の説明と「✓ 説明の数字は、すべて表の値と一致」
- 評価の表（順位の相関 0.89、遅延の誤差 18ms → 13ms）
